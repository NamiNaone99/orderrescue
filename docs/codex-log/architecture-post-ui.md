## Four proposals awaiting a decision

1. **Interpret context.** A strict 1–500-character request is validated before storage or quota. The route then reads the full scenario in either mode. The server builds instructions from the scenario date, warehouse IDs/names and shifts. A provider receives the trimmed operator message, instructions, strict schema and model settings with `store: false`; the backend does not attach its SKU catalog, customer references, orders, receipts or stock. Operator-entered free text itself is transmitted. SKU membership and evidence checks run on the server. Mocked SDK regressions cover request shape, disabled SDK retries and sanitized failures. A dedicated metadata projection remains a proposal. An eventual metadata success must preserve a degraded scenario's write refusal until a successful operational read. [Interpret route, lines 13–18](https://github.com/NamiNaone99/orderrescue/blob/5f3d48f/app/api/interpret/route.ts#L13) · [Prompt, lines 3–15](https://github.com/NamiNaone99/orderrescue/blob/5f3d48f/lib/interpreter/prompt.ts#L3) · [SDK request, lines 10–30](https://github.com/NamiNaone99/orderrescue/blob/5f3d48f/lib/interpreter/openai.ts#L10) · [Provider tests](https://github.com/NamiNaone99/orderrescue/blob/5f3d48f/tests/interpreter/openai.test.ts#L51)
2. **Database-filtered Plan and State.** Plan provides a SKU to Store. The Supabase adapter selects seven scenario-wide fields from one invoker-security view, validates the returned shape, and filters in TypeScript. State reads the same view. The digest is computed first from all ordered stock identity/revision tuples and order ID/status pairs. The unbooked desk checks the used stock rows and every affected order status, including unallocated orders. It polls every five seconds while visible and reads immediately after Plan. Public State omits customer references and idempotency keys. The current candidate for a narrower Plan read would retain the selected SKU's stock from **all** warehouses, open affected orders/lines and a transactionally consistent whole-scenario version. It would need to preserve unknown SKU vs known SKU with zero affected orders, the 60/61 gate, reasons, costs and six-field booking hash. A projected State polling read is a separate decision. [Plan service](https://github.com/NamiNaone99/orderrescue/blob/5f3d48f/lib/api/planning.ts#L9) · [Adapter](https://github.com/NamiNaone99/orderrescue/blob/5f3d48f/lib/store/supabase.ts#L68) · [SQL view](https://github.com/NamiNaone99/orderrescue/blob/5f3d48f/supabase/migrations/20261121044705_init.sql#L92) · [Digest and filtering](https://github.com/NamiNaone99/orderrescue/blob/5f3d48f/lib/store/types.ts#L39) · [Public State](https://github.com/NamiNaone99/orderrescue/blob/5f3d48f/lib/api/state.ts#L5) · [Desk stale checks](https://github.com/NamiNaone99/orderrescue/blob/5f3d48f/lib/client/plan-changes.ts#L7)
3. **Template interpretation.** The form submits an incident directly to Plan. It uses zero provider calls, as do State, planning, budget edits, the demo event and booking. Free text in live mode can use one primary and one fallback, each checked against quota; offline/no key uses zero. The separate offline item in the public attempts list is a local answer. Offline matching accepts only normalized stored samples. The contract permits `offline` and `openai:…`; the desk displays the reported source. The guide's choice of a stored example still activates the ordinary interpreter. No strict template parser or `rules` source exists. Introducing either requires a decision across the SPEC, validator, UI and eval. Malformed templates, unchanged offline semantics and zero attempted calls/debits on a successful rule would need coverage. 4. **Telemetry and AC-26.** Per-attempt outcome, sanitized reason and model timing exist; the HTTP response includes source, attempt list, chain latency and quota status. The adapter discards provider usage, and the Store emits no per-route byte/latency series. The stored three-row offline smoke scored 3/3 outcome kinds, 1/1 incident field sets and zero false incidents. It includes two development rows and one held-out row. Decisions remain on minimal correlated usage, separating unknown usage from zero calls, sampled Store/AI/end-to-end timings and evaluation on an independently checked corpus. ## Reservation and presentation boundaries

The route verifies the submitted hash and budget, then invokes Store without replanning. The memory critical section and the single `reserve_plan` RPC replay a matching idempotency key and hash, reject conflicts and check open orders, exact quantities, authoritative price, expected revisions and net available stock. SQL locks the key and rows, groups lines by stock row and increments each row's revision once. Refusal rolls back all changes. A failed Supabase operational read can serve memory; writes refuse for that scenario until an operational refresh succeeds. A successful health read alone does not clear a scenario's fallback flag. The view/RPCs are restricted to the service role, and tables have RLS. T15's 19/19 hosted Store-contract results are historical. The current check used mock transport and the local memory contracts. [Booking service](https://github.com/NamiNaone99/orderrescue/blob/5f3d48f/lib/api/planning.ts#L27) · [Memory](https://github.com/NamiNaone99/orderrescue/blob/5f3d48f/lib/store/memory.ts#L43) · [SQL transaction](https://github.com/NamiNaone99/orderrescue/blob/5f3d48f/supabase/migrations/20261121044705_init.sql#L125) · [Fallback guard](https://github.com/NamiNaone99/orderrescue/blob/5f3d48f/lib/store/index.ts#L13) · [Hosted contract record](../CODEX_LOG.md)

TOUR runs on hero, resets via the normal hero-only desk action, takes its numbers from the live plan and presses the existing controls. Review and submission require separate actions. Reload resolves the saved public receipt ID via State. T19 renders ledger evidence at build time. Neither presentation feature introduces a model call, store implementation, plan algorithm or booking route of its own. The ordinary free-text hero still uses Interpret. The release owner's eight-step production run verified the stale refusal in the UI and a single ฿32 booking.
