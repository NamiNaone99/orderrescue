# T16 stale plan detection and refusal

21 Nov 2026, 12:15–12:25 ICT · Codex local on Windows · GPT-6 · Node 22 · pnpm 9.15.9

The desk lists each scenario's registered events, refreshes stock after an action and polls every five seconds while a plan or receipt is visible. It checks the stock revisions used by both strategies and the status of every affected order. A relevant change dims the original plan, disables confirmation, announces the change and focuses Replan. A definitive booking refusal closes the dialog and discards its key. A transport failure retains the confirmed payload and its key for receipt recovery.

## Observations

- The original joint plan served both orders for ฿88. The B slip showed “13:30 → 14:30” within the smoke test's five-second deadline. Exactly one plan request had been sent. Clicking Replan sent a second request, producing 1/2 at ฿32 with #102 through B and #101 requiring a person.
- Posting the original rows after the slip returned `409 STALE_STOCK`. The complete projected state was identical before and after the rejected request. Racing separate real reservations produced `IDEMPOTENCY_CONFLICT` and `ORDER_ALREADY_RESERVED`. Each refusal closed the original dialog, identified the reason and focused Replan. The next confirmation after the slip used a fresh key.
- A hidden tab made zero state requests during a 5.4-second check. Returning to the tab refreshed immediately and detected an externally applied slip. In a separate visible-tab check, a passive poll detected an external slip in 4,928 ms, closed the open confirmation dialog and focused Replan. The plan request count stayed at one.
- Dropping a real HTTP 201 after the server committed left the dialog available while a poll showed B's free stock at zero. Retrying the identical body and key replayed HTTP 200 and displayed the receipt. After an external loopback reset, polling showed B's free stock return to eight and the replayed receipt stayed unchanged.
