# T22 F1. Recover the receipt after a storage error

21 Nov 2026, Bangkok. Codex local on Windows, GPT-6. The T22 review found that a successful inventory poll could clear a booking's confirmation after an indeterminate storage error. This correction covers receipt replay under AC-15 and the booking protocol in SPEC §8.

## Reproduction and correction

The Chromium test submits the actual two-row hero reservation to the local memory store. After the server creates the receipt and returns HTTP 201, Playwright replaces the response delivered to the browser with a typed HTTP 503 `STORAGE_UNAVAILABLE`. The next inventory poll is real. On the original build at `17a9dc5`, the desk showed warehouse B with 0 free units, then its confirmation button detached before the operator could retry. The test failed on that second click.

The desk now keeps the original confirmation when that storage error makes the outcome uncertain. Polls continue to update visible stock. In both the HTTP 503 and existing connection-reset cases, the operator retried the byte-identical request, including the idempotency key. The server returned HTTP 200, the exact original receipt and `replayed: true`. The final snapshot contained one reservation. A definitive 409 still uses the stale-plan path, and the unhealthy-storage guard still disables confirmation.
