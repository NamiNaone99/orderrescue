## Part one

The deployed smoke workflow accepts a success event from Vercel's GitHub bot for the OrderRescue project or a manual launch on the repository's main branch against canonical production. The official payload provides `url`, `git.ref`, `git.sha`, `environment`, `project.id`, `project.name` and the successful state. Verified immutable URLs are restricted to the project's team. All deploy checks share one GitHub concurrency queue because they operate on the same synthetic hero. [Vercel GitHub integration](https://vercel.com/docs/git/vercel-for-github#repository-dispatch-events) · [Typed package and payload example](https://github.com/vercel/repository-dispatch/tree/main/packages/repository-dispatch) · [GitHub concurrency settings](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)

The workflow checks out the deployed SHA and a trusted harness. It runs a reviewed main-line deployment's own smoke suite when available. Unreviewed previews run the main harness without either repository secret; a protected, unreviewed preview reports its access refusal. Reviewed private deployments can exchange the bypass header on the verified origin with redirect following disabled, then use host-only browser cookies. Neither original secret is inherited by browser workers. Authentication failures report the endpoint status without request headers. [Vercel automation protection](https://vercel.com/docs/deployment-protection/methods-to-bypass-deployment-protection/protection-bypass-automation)

The hosted suite checks the expected commit and healthy storage, resets only `hero` before and after, and waits through the documented reset window when necessary. The two mutating tests also start from their own hero seed. The read-only home and health tests make no resets. Both live and offline interpretations are judged on the incident and plan they produce. The PowerShell smoke and hero-only reset commands are in the README.
