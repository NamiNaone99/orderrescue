# ระบบที่มีอยู่และหลักฐานสำหรับออกแบบ Agent

อ้างอิงด้วยรหัสใน [ทะเบียนและ Document Cards ด้านระบบ](sources-systems.md) ตัวเลขราคาเป็นภาพที่ตรวจ ณ 21 พ.ย. 2569 ตามเวลาไทย ปีและระดับความมั่นใจของผลที่อ้างแสดงในตารางหรือการ์ดประจำแหล่ง

## H5 · ระบบเดิมทำได้แค่ไหน

**คำตัดสินสำหรับความสามารถทั่วไป: ไม่ผ่าน** เอกสารแสดงว่าระบบที่มีอยู่ทำทั้งเลือกแหล่งทดแทน ทบทวนข้อผูกพันเดิม และส่งแยกได้แล้ว **คำตัดสินสำหรับต้นทุนและความเหมาะสมในกลุ่มที่เจาะจง: ข้อมูลไม่พอ** หลักฐานยังไม่ครบตาม Kill Criteria ที่ต้องทดสอบ SLA และค่าเปิดใช้ของบัญชีเดียวกัน เทียบกับข้อเสนอของ OrderRescue [K01, K03–K07, K20, K24]

**ทดสอบคู่เทียบกับออเดอร์เดียวกัน** ขอให้ระบบที่ลูกค้าใช้อยู่แสดงการนำเข้าเหตุ ตัดเฉพาะ stock/node ที่ใช้ไม่ได้ หาออเดอร์ที่ผูกไว้เดิม ทำรายการแผนโดยคำนึง cutoff/คิวหยิบ/สิทธิ์ และยืนยันการจองสำเร็จ จากนั้นขอต้นทุนเพิ่มรายปีรวม license, integration, setup, training, support และค่าเวลาคน เทียบกับการทำแบบ manual และการใช้เครื่องมือที่มีอยู่แล้ว ผลต่างต้องวัดบนออเดอร์และ SLA ชุดเดียวกัน [ข้อเสนอจาก K01, K05, K06, K20]

| ตรวจสต็อกที่จองได้ | SKU × node × lot/serial, จำนวน on hand ที่ขายได้, reservations, safety stock และ blocked/damaged พร้อม timestamp/version ของแหล่งอ้างอิง ตรวจ ready time และความเชื่อมั่นจาก cycle count | หักแต่ละหมวดครั้งเดียวตามนิยามใน ERP/WMS ตรวจ physical pick และ reservation outcome โดยเฉพาะจำนวนใกล้ศูนย์ [K05, K06, K12, K15, K18] |
| ตรวจเส้นทางและความสามารถ | รหัสไปรษณีย์ผู้รับ origin ที่ช่องทางอนุญาต carrier/rate, cutoff, ความจุคลัง/รถ, เวลาหยิบแพ็กและเดินทาง, เส้นทางเปิดจริง, น้ำหนัก/ขนาด แยกความจุการหยิบออกจากความจุขนส่ง | ใช้เที่ยวรถและ SLA ที่ทีมใช้งานจริงในช่วงเหตุ รวม exception ที่เปลี่ยนผลย้อนหลังได้ [K01, K06, K17] |
| เสนอแผน | ใช้กฎธุรกิจเป็น hard constraints ก่อนจัดอันดับ พิจารณาส่งครบจากจุดเดียว การโอนเข้าคลังหลัก การส่งแยก และการเสนอวันใหม่ หากไม่มีทางเลือกแสดงเหตุผลและส่งต่อผู้มีอำนาจ ใช้กำไรส่วนเพิ่ม ต้นทุนส่ง/หยิบเพิ่ม เวลา และสต็อกที่ต้องกันให้ลูกค้าอื่นในการจัดลำดับ | เทียบแผนเดิมแบบคนจัด ระบบเดิมที่ตั้งค่าครบ และแผนรวมทั้งชุดบนทรัพยากรเดียวกัน [K01, K05, K06, K13–K16, K19–K20] |
| ยืนยันและลงมือ | ให้ OMS/WMS ถือยอดจริง ตรวจ version ก่อนจอง ใช้ idempotency key สำหรับ retry ตรวจผลจองก่อนปลดแผนเดิมตามความสามารถระบบ และบันทึกผู้อนุมัติ เหตุผล และคำตอบจากปลายทาง | ทดสอบพร้อมกันหลายคำขอและความล้มเหลวกลางทาง ให้เจ้าหน้าที่กระทบยอดก่อนส่งคำสั่งถัดไป |

ตัวแปรต้นทุนขั้นต่ำของแต่ละทางเลือกคือ ค่าขนส่งและย้ายสินค้า ต้นทุนหยิบแพ็กซ้ำ ค่าแยกพัสดุ ค่าชดเชย SLA ความเสี่ยงสินค้าเสียหาย และกำไรที่กู้ได้หลังหักต้นทุนส่วนเพิ่ม เลือกกฎ priority ร่วมกับธุรกิจ เช่น วันครบกำหนด การกันสต็อก Key Account มูลค่าส่วนเพิ่ม หรือลำดับที่ตกลงในสัญญา และแสดงเหตุผลเมื่อการรักษาสัญญาหนึ่งกระทบออเดอร์อื่น [ข้อเสนอจาก K05, K06, K13–K15, K19]

**เงื่อนไขส่งต่อคน** SKU มีข้อกำกับอุณหภูมิ ล็อต ซีเรียล หรืออายุคงเหลือ, ลูกค้าที่ล็อกวันและจำนวน, การเปลี่ยน shipment ที่จองหรือส่งต่อ 3PL แล้ว, เงื่อนไขส่งครบ/แยกส่งตามสัญญา, เปลี่ยนปลายทางหรือ carrier ที่สิทธิ์ไม่ชัด, ต้นทุนเกินอำนาจอนุมัติ, stock/route ขาดหลักฐานยืนยัน และ blackout ที่ทำให้คลังสำรองพึ่งเส้นทางเดียวกัน [ข้อเสนอจาก K05, K06, K11, K15, K17, K18, K20] สัดส่วนในไทย **ไม่พบข้อมูลสาธารณะ** ให้คำนวณจากจำนวนออเดอร์ที่ติดอย่างน้อยหนึ่งเงื่อนไขหารด้วยออเดอร์กระทบทั้งหมด แสดงจำนวนต่อเหตุและต่อประเภทออเดอร์ ใช้ union เพื่อป้องกันการนับออเดอร์ซ้ำข้ามเหตุผล

**เกณฑ์ข้อมูลก่อนอนุมัติการจอง:** เทียบผลจองกับเวลาหยิบจริงและตรวจ drift แยกตามคลัง/เวลา/สถานะ ถ้าไม่มีข้อมูลพร้อมจองที่เชื่อถือได้ ให้ทำรายการผลกระทบและคำขอตรวจนับก่อนส่งแผนจอง ช่วงเริ่มทดลองวัด time-to-decision, อัตราหยิบได้จากจุดแรก, on-time complete orders ต่อออเดอร์กระทบ, cancel ต่อออเดอร์กระทบ, parcel/order, ค่าขนส่งเพิ่ม, ความคลาดเคลื่อนของยอดจอง และกำไรส่วนเพิ่มบนชุดเดียวกัน แยกเป้าหมายส่งทันเดิม ออเดอร์ที่ลูกค้ายอมเลื่อน และเคสที่กู้ไม่ได้ เพื่ออ่านผลตาม SLA จริง [ข้อเสนอจาก K06, K12–K20]
