# Deploy plan

## 1. Environments

| Environment | Where | Storage | Interpreter | Purpose |
|---|---|---|---|---|
| Local | `pnpm dev` on each laptop | memory | offline (or openai with a local key) | Development, no-network fallback demo |
| CI | GitHub Actions | memory | offline | Lint, typecheck, tests, e2e. No secrets |
| Preview | Vercel, one URL per PR | memory | offline | Review UI changes. Keeps previews from polluting the shared database and from spending API credit |
| Production | Vercel, `https://<app>.vercel.app` from `main` | supabase | openai | The judge-facing live site |

Rules:

- The GitHub repo is in the Owner's **personal** account and the same person owns the Vercel Hobby project (Hobby cannot import organization repos). Owner = P2 unless agreed otherwise.
- Function region Singapore (`sin1`); Supabase project in Singapore.
- Production is the only environment that holds the OpenAI and Supabase secrets, unless a preview needs them for a specific test.
- Vercel Hobby limits: 100 deployments per day, 1 concurrent build, runtime logs kept 1 hour. Batch commits and merge PRs in groups.

## 2. Environment variables

| Name | Local | CI | Preview | Production | Notes |
|---|---|---|---|---|---|
| `STORAGE_MODE` | `memory` | `memory` | `memory` | `supabase` | Missing or unknown value means `memory` |
| `INTERPRETER_MODE` | `offline` | `offline` | `offline` | `openai` | Missing key forces `offline` |
| `OPENAI_API_KEY` | optional | none | none | set, sensitive | Server only |
| `OPENAI_MODEL` | `gpt-6-luna` | none | none | `gpt-6-luna` | Verify the id |
| `OPENAI_FALLBACK_MODEL` | `gpt-6.2-sol` | none | none | `gpt-6.2-sol` | Verify the id |
| `SUPABASE_URL` | optional | none | none | set | Server only |
| `SUPABASE_SECRET_KEY` | optional | none | none | set, sensitive | `sb_secret_...`; bypasses RLS; server only |
| `DEMO_RESET_TOKEN` | any (`local-token` default in e2e) | `ci-token` | set | set, sensitive | Needed only to reset `real-day` or all scenarios; `hero` resets without it. Also a GitHub secret for the deployed smoke run |
| `INTERPRET_DAILY_CAP` | `500` | none | none | `2000` | Hard cap on model calls per instance per day |
| `INTERPRET_BURST` | `30` | none | none | `30` | Per-IP bucket size on `/api/interpret` (the venue shares one public IP) |
| `INTERPRET_REFILL_MS` | `2000` | none | none | `2000` | One token back per this many milliseconds |

Commands (Vercel CLI 64.6 or later): `vercel link`; `vercel env add NAME --environment production --sensitive` per secret; `vercel env pull .env.local` (sensitive values are not pulled back, so keep `.env.local` by hand). The dashboard works as well. Redeploy after changing variables.

Never prefix any of these with `NEXT_PUBLIC_`. Commit `.env.example` with names and safe defaults only.

## 3. Deploy flow

1. Work on a branch, open a PR. Vercel comments a preview URL. CI runs.
2. Review by tier (`CODEX_TASKS.md`, "How to run a task"): full Codex review and CI wait for T03, T04, T06, T11, T15, T16; local acceptance checks for the rest. Human reads every diff. Merge.
3. Merge to `main` deploys production. The `e2e-deployed` workflow (if T21 part 1 was built) runs the smoke test against it; otherwise run `pnpm smoke` by hand.
4. The person who merged checks `/api/health` shows the new commit.
5. The first deploy happens at 10:15-10:45, straight after the first push (T08), so that protection settings, collaborator builds and font fetches are found early.

Deployment Protection: turn Vercel Authentication off for the project so previews and production open without a Vercel login, or keep it on and use the Protection Bypass for Automation secret in Playwright. Confirm in a private window. The default for new Hobby projects was not confirmed in research; check the setting.

Manual deploy if Git deploys do not trigger (for example commits by a collaborator are not built): the Owner pulls `main` and runs `vercel deploy --prod`.

## 4. Database migrations and seed

- SQL files in `supabase/migrations/<timestamp>_init.sql` (tables, constraints, RLS on, revokes, functions `reserve_plan`, `apply_demo_event`, `reset_demo`) and `supabase/seed.sql` (hero rows written by hand in SQL to match `lib/scenarios/hero.ts`, real-day rows generated by `pnpm data:seed-sql`).
- A test compares the seed's hero rows with the TypeScript fixture so they cannot drift.
- Apply (primary route, about 3 minutes): paste the migration, then the seed, into the Supabase Dashboard SQL Editor.
- Fallback: `pnpm dlx supabase login`, `pnpm dlx supabase link`, `pnpm dlx supabase db push` (needs the Postgres ports open at the venue; flags not verified, check `supabase db push --help`).
- The seed also holds scenario `hero-test` (a copy of hero) for the contract tests; it is never listed in the UI.
- Real-day rows need a second seed apply after T13 merges; do it only if T13 has merged by 15:00.
- The app talks to Supabase **only over HTTPS** with `@supabase/supabase-js` and the secret key, on the server. No Postgres connection string anywhere in the app or in Vercel.
- Schema changes after the first apply: add a new migration file; do not edit the applied one. After 15:45, no schema changes.
- After applying: run `pnpm test:db` once (store contract and concurrency suite against the hosted project, scenario `hero-test` only) and record the result. Run it before production is switched to `supabase`, never during judging.
- **Hard stop 15:00:** if `pnpm test:db` is not green by 15:00, production stays on memory (cut-line 7).

## 5. Demo reset and shared state

- `POST /api/demo/reset`. Body `{ "scenario": "hero" }` needs no token (limited to 6 per minute per IP). `{ "scenario": "real-day" }` or `{}` (all) needs the header `x-demo-token`. Supabase mode calls `reset_demo()`; memory mode rebuilds the in-memory state from the fixtures.
- UI: the header Reset button and the `เริ่มเหตุการณ์ใหม่` button after a booking reset the hero scenario without a token, so any visitor (or a judge on their own phone) can bring the demo back. In other scenarios Reset opens a dialog asking for the token (kept in `sessionStorage` for the tab).
- The live site is one shared demo state: one visitor's booking, slip event or reset is seen by everyone. Say so if asked. Per-visitor workspaces (section 5a) are stretch task S0.
- Command line (PowerShell): `curl.exe -X POST -H "x-demo-token: $env:DEMO_RESET_TOKEN" -H "content-type: application/json" -d "{}" https://<app>.vercel.app/api/demo/reset`
- Reset before every judging rotation and at the start and end of every e2e run against a deployed URL. Do not run smoke against production while a judge is using the site.
- Memory mode on Vercel is per instance and not durable: plan, demo event, poll, reserve and reset can hit different instances, and a cold start wipes the state. It is acceptable for previews and as an emergency fallback, and the UI badge says `DB: memory`.
- While production is on memory, judge the MVP gate and run `pnpm smoke` against production but treat a single failure caused by lost state as expected; retry once after a reset. If Supabase is cut (cut-line 7), the judged demo runs from rung 4 (laptop, `pnpm build && pnpm start`), the live URL is shown as the public copy, and the presenter says storage there is in memory per server instance.

## 5a. Per-visitor workspace (stretch S0, not in the baseline)

Every browser gets a workspace id `ws` (12 random characters, cookie `or_ws`, also accepted as `?ws=`). All routes resolve the effective scenario id as `<scenario>~<ws>` (`scenario_id` is already the first key column). On first use the rows are cloned from the seed (`reset_demo(p_scenario, p_ws)`; memory: clone the fixture). `POST /api/demo/reset` with the caller's own `ws` needs no token. `x-demo-token` is then only needed for `{ "all": true }`, which deletes every workspace. `reset_demo` also deletes workspaces older than 2 hours. Smoke and e2e runs use `ws=smoke-<run id>` and never touch other workspaces, so specs may run in parallel.

## 6. Rate limiting and cost control

Everyone at the venue (team, judges, other teams) shares one public IP, and the e2e suite presses Analyse many times from one address. Limits are sized for that.

Three layers on `/api/interpret`:

1. **Vercel WAF rule** (Hobby allows one). Optional; skip it if behind. Path equals `/api/interpret`, rate limit, fixed window 60 s, 120 requests per IP, respond 429. Publish after T11. Keep it on this one path: a rule on all of `/api/` would count the 5-second state polling of every open desk behind the shared IP.
2. **In-code limiter**: per-IP token bucket (burst `INTERPRET_BURST`, default 30; one token back per `INTERPRET_REFILL_MS`, default 2000) and the per-instance daily cap `INTERPRET_DAILY_CAP`. It is applied only when the request would call OpenAI; in offline mode it is skipped. When the bucket or the cap is empty the route answers with the offline interpreter and `rate_limited: true`, never a 429, so sample messages always work.
3. **Input and call limits**: message at most 500 characters; `max_output_tokens` set; client `timeout: 9000` and `maxRetries: 0`; at most two model attempts per request (18 s worst case, then offline); `export const maxDuration = 30` on the route; `store: false`.

Other routes (task T21 part 2): `/api/plan` and `/api/reservations` share a per-IP bucket (burst 20, refill 1 per second, `429 RATE_LIMITED`); request bodies over 16 KB are rejected with 413; `/api/plan` rejects more than 60 affected orders with `INVALID_INPUT`. The tokenless hero reset is limited to 6 per minute per IP (T06). `/api/demo/event` only applies predefined events, and a reset restores state, so abuse costs nothing but a reset.

Also: a monthly budget on the OpenAI project; a separate key for local development so the production key can be revoked alone. Each member reads their Codex and API credit balance aloud at 12:30 and 14:30; under 30% left means default effort only and no cloud attempts. After finals: revoke the OpenAI keys and the Supabase secret key, rotate `DEMO_RESET_TOKEN`.

## 6a. Headers and indexing (task T21 part 2)

`next.config.ts` `headers()`: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: camera=(), microphone=(), geolocation=()`, and, in production builds only, `Content-Security-Policy: default-src 'self'; img-src 'self' data:; style-src 'self' 'unsafe-inline'; script-src 'self' 'unsafe-inline'; connect-src 'self'; frame-ancestors 'none'`. Relax or drop the CSP if any page breaks, and note it; it is the first thing to remove if the site misbehaves near the freeze. `app/robots.ts` disallows all.

## 7. Monitoring

- `/api/health` returns `ok`, `storage`, `interpreter`, `model`, `degraded`, `commit` (shape in `SPEC.md` section 5). In Supabase mode it also does one cheap read; on failure it reports `storage: "memory"` and `ok: true` with `degraded: true`.
- Every response carries `x-request-id`; error messages on screen show its short form, and every server log line includes it (Hobby keeps runtime logs for 1 hour).
- The header badges show the same information to everyone looking at the screen.
- Structured `console.log` lines on the server for each interpret (model used, latency, outcome, validation issues; never the key, and the message text only as a length) and each reservation (code, receipt id). Visible in Vercel runtime logs for 1 hour.
- The `e2e-deployed` workflow (if built) is the per-deploy check. During judging, one teammate runs `pnpm smoke` against production before each rotation, not during one.
- No third-party monitoring service.

## 8. Rollback

- Vercel dashboard > Deployments > choose the last deployment that passed smoke > Instant Rollback (or Promote). Takes seconds and needs no build.
- Keep a note of the last known-good deployment URL in `docs/CODEX_LOG.md` after each successful smoke run.
- Code rollback: `git revert <merge commit>` on `main`, never a force-push.
- Database: `reset_demo()` restores data. A bad migration after first apply is fixed by a new forward migration; if that fails, switch production to `STORAGE_MODE=memory` and redeploy.
- Last merge to `main` 16:30. No pushes after 16:30 except a rollback. This leaves time for the Vercel build, a smoke run and a rollback before submitting at 16:50.
